# Architecture Decision Record

Five decisions, recorded in the order of the required topics. Entries 1, 2 and 5 were recorded on 2026-09-24, entry 3 on 2026-09-27 and entry 4 on 2026-10-04.

## [1]. Use Django with server-rendered pages and built-in authentication
Date: 2026-09-24
Status: Decided
Context: Python is the author's strongest language, and attendees need persistent username/password accounts. Admins need to curate genres, review proposed locations and reports, and manage accounts.
Decision: Use Django with its authentication, admin, ORM, and migrations, serving HTML templates, plain CSS, and JavaScript from the same application. Use built-in Django JSON responses for map queries rather than adding a REST framework.
Alternatives considered: Flask was considered for its smaller core, but would require assembling more account and administration functionality. React Native/Expo and React were considered for future portability, but add unfamiliar frontend tooling and complicate the one-manifest requirement; plain HTML/CSS matches current experience.
Consequences: Django's integrated features have concrete uses, while one Python application remains the runtime boundary. The author must learn and explain Django conventions; a later React frontend would replace presentation code while reusing suitably separated business logic.

## [2]. Separate discovery from attendance groups inside one monolith
Date: 2026-09-24
Status: Superseded by [6]
Context: The product helps people find music events and optionally find company, and the assignment requires two distinct SQLite-backed domains. Map display alone is not an independent backend domain.
Decision: Use a discovery app for genres, venues, events, listening references, review/report flows, and filtering, and a groups app for groups, join requests, memberships, photos, and messages. Keep business rules separate from HTTP rendering, with groups obtaining event identity and necessary event information through a small discovery interface.
Alternatives considered: Events and a basic venue directory were considered as the two domains, but groups offers a more distinct user purpose. A single undifferentiated application module would make responsibilities and a future separation harder to explain; separately deployed services are prohibited now.
Consequences: Both domains share Django authentication and one SQLite database but have distinct data ownership and responsibilities. A future service split would need explicit handling of shared identity, event references, and consistency; the module split alone does not solve those issues.

## [3]. Separate reusable music and venue data from event and group state
Date: 2026-09-27
Status: Superseded by [7]
Context: Events can share approved venues while having different genre tags, times, and groups, so editing one event must not change another. Users also need tracked-event updates and one group membership per event.
Decision: Use the relational schema in SCHEMA.md: event-to-venue references, category/tag link tables, separate curated and event listening references, event follows/change records, and group membership/request/ban/message records. Derive tempo from admin-curated category/tag ranges, and use transactional domain operations for membership switches, ownership transfer, and notification creation.
Alternatives considered: Copying venue details into every event would duplicate approval state; editing the shared venue when moving an event would affect other events. Event BPM input was rejected in favor of curated estimates, while a single membership status record was rejected in favor of separate current memberships and request history.
Consequences: Reusable records keep location review and genre colors consistent, while event-specific relationships preserve independent edits and optional group participation. Cross-record rules cannot all be expressed as simple row constraints and need guarded transactional operations; the schema and diagram must be reconciled with actual migrations during implementation.

## [4]. Testing Approach
Date: 2026-10-04
Status: Decided
Context: The assignment guidelines require tests and 70% coverage. The app depends on a shared database.
Decision: I relied on AI to write the automated backend tests as part of building and implementing the services of the app. The interfaces and UI were tested by hand between iterations. I preferred to test the frontend and UI by hand, to experience how the app felt, looked, and behaved from the perspective of an actual user.
Alternatives considered: I chose not to write the tests by hand to dedicate more time to creative work in the app, which is where I felt that I was strongest and most productive. To test the whole app, especially backend endpoints by hand, would have been inefficient and counterproductive.
Consequences: I was able to dedicate a much greater amount of time to UI and functionality design, instead of manually writing and/or running tests. The full automated suite of 216 tests runs in about a minute, and was able to reach 96% coverage, which would have been a very time consuming goal had the tests been written by hand. A risk of checking UI and frontend by hand is the opportunity for unforeseen circumstances to result from non-rigorously tested code.

## [5]. Defer real-time chat and external ticket purchasing integrations
Date: 2026-09-24
Status: Decided
Context: Attendees need basic coordination and access to tickets, but the assignment deadline and single-process constraints favor a limited first version. The user chose an in-app message board and external listening/ticket references.
Decision: Provide a members-only text message board that loads on page opening or refresh and ordinary external ticket links. Do not build real-time chat, push/email notifications, ticket checkout integrations, or hosted audio in this version.
Alternatives considered: An external group-chat link would be simpler but moves coordination outside the app. Live messaging and integrated ticket purchasing would offer richer interaction but add protocols, third-party dependencies, and implementation work beyond the current need.
Consequences: Groups can coordinate through persisted messages without real-time infrastructure, and ticket purchases remain with external providers. Users must refresh to see new messages and leave the app to buy tickets or listen to linked music.

September 27 scope clarification: in-app notifications for tracked-event changes and group offers are now included; live delivery and push/email remain deferred. This amendment preserves the earlier decision date rather than creating a sixth ADR entry.

October 2 amendment to entry 5: the group chat is now live. The page polls a small endpoint (`/groups/<id>/chat/`) every three seconds while the tab is visible, sends a fingerprint of what it already shows, and the server answers "nothing new" or returns fresh chat and member HTML. Sending also happens in the background. This keeps the single-process, no-extra-service design: it uses ordinary short requests, not WebSockets, a message queue or a worker. The tradeoff is up to about three seconds of delay and a steady trickle of cheap requests per open chat. Push or email notifications, ticket checkout and hosted audio remain deferred. This amendment preserves the original decision date rather than creating a sixth entry.

Status note (2026-10-04): the chat part of this decision was later reversed (see the October 2 amendment above). The deferral of ticket checkout, push or email notifications and hosted audio still stands.

## [6]. Extract Discovery and Groups along the existing domain seam
Date: 2026-11-16
Status: Decided
Context: Assignment 2 requires two independently running services with separate data and a static UI. ADR 2's domain seam still fits, but shared authentication, event foreign keys, and a combined notification table prevent independent operation.
Decision: Keep Discovery responsible for music/event discovery, accounts and event-follow notifications. Groups owns attendance records and group notifications. Replace cross-domain relations with plain stable IDs and HTTP contracts detailed in SERVICE_BOUNDARIES.md. Discovery validates credentials for protected Groups requests, while public event details support the group creation/join flow. Each service owns its own inbox records. Validate remote data before local transactions and return explicit 401/403/404/409/503 responses according to the contract. Extract the existing Django model and service logic incrementally before replacing the root runtime.
Alternatives considered: A third identity service violates the two-service constraint. Copying passwords into both databases duplicates account security state. Locally verified signed tokens reduce identity calls but introduce signing-key rotation and revocation complexity. Keeping Django templates would violate the static-UI requirement. Memory-only browser bearer storage avoids persistent token storage but requires sign-in after a full reload.
Consequences: The original Discovery/Groups seam holds, with explicit ownership of shared concerns. Protected Groups operations depend on Discovery availability and fail clearly when identity validation is unavailable. No foreign key or transaction spans services, so event availability can change after a successful check. Historical Groups records retain stable remote IDs. Idempotent membership operations and keyed group creation prevent duplicates on retries. Event followers retain their notification behavior; group membership alone does not imply following an event. Extraction is staged; deployment, data import, final authentication implementation and the complete static UI are not yet delivered by this decision.

## [7]. Preserve owned data with Django migrations and an offline split import
Date: 2026-11-18
Status: Decided
Context: Each service must move from SQLite to its own SQL Server database without losing existing records. SQL Server has different NULL uniqueness and index-width behavior, and the original accounts, event references and notifications span the old monolith. Applied migrations already exist and must remain unchanged.
Decision: Keep Django's migration history and add new migrations. Use mssql-django with ODBC Driver 18 and encrypted connections, bounded login/query timeouts and transient connection retries. Export the source consistently while writes are stopped, preserve account/event/group/message IDs, resolve content types/permissions/roles by natural keys, and import only into an empty owner database. Discovery owns password hashes and permission grants; Groups receives credential-free account references and plain event IDs/snapshots. Record an export fingerprint for repeat-safe import. Split notifications by their owning domain. Validate the completed fixture's foreign keys before committing the import. Never copy live sessions. Details and operator commands are in DATA_MIGRATION.md.
Alternatives considered: Recreating tables or reseeding on deployment would lose data. Copying raw permission/content-type IDs could silently grant the wrong role when migration-generated IDs differ. Sharing the monolith database would violate ownership. A separate migration framework would duplicate Django's existing schema history. SQL Server uses a case-insensitive database collation with ordinary name uniqueness constraints to preserve the case-only genre duplicate rule, since its backend does not create expression indexes. Wide recording URLs use a SHA-256 uniqueness key, with an in-place backfill, instead of indexing the full URL. Nullable group-request notification keys are uniquely indexed only when present.
Consequences: Existing cross-domain foreign keys become stable IDs with HTTP eligibility/identity checks and historical snapshots, so cross-service referential integrity and atomicity are unavailable. Short Groups read-check-write transactions take a database-scoped application lock; HTTP happens beforehand. This deliberately serializes local writes at current traffic and requires a finer lock strategy at higher load. Startup schema migrations take a separate session-scoped database lock so overlapping revisions cannot migrate concurrently. Recovery first halts deployment/traffic and adds a forward corrective migration, never edits an applied file or fakes migration history. If a migration causes irrecoverable data loss, stop and coordinate point-in-time backup recovery with the professor within the resource quota; do not automate destructive database replacement. Keep source exports and backups private, verify retained IDs/rows before resuming, and copy each owner's uploaded files separately. Local SQL Server tests prove migration/import behavior; the required before/after migration evidence on Azure still needs two actual deployments with pre-existing Azure data.


## [8]. Define the student Azure runtime with Terraform and scoped OIDC
Date: 2026-11-20
Status: Decided; initial Azure deployment verified 2026-11-20
Context: The professor's November 20 student deployment guide explicitly replaces the original shared-class contract. Assignment 2 now uses an own Azure for Students subscription, Storage static hosting, a managed identity with GitHub OIDC, and the SQL student free offer. The original Static Web App/class service-principal plan is obsolete. Actual subscription eligibility, allowed regions and capacity must be checked before provisioning.
Decision: Use the resource group rg-<IE-prefix>, one Standard_LRS StorageV2 account for the static UI and a separate private Terraform-state container, one own managed identity, one Consumption Container Apps environment and its metered Log Analytics workspace, two Container Apps, one SQL server and two domain databases. The Terraform root in infra/ owns the runtime after documented initial setup. Pin Terraform and providers and validate the resource contract with mocked providers in CI. Scope OIDC Contributor to this group and Blob Data Contributor to the own UI/state Storage account, using Azure AD rather than account keys for blob/state access; register both named and numeric repository subjects for main. Pipeline changes follow same-SHA CI. Keep all runtime secrets in GitHub/Container App secrets, and state in the private blob backend with lease locking. Never publish state with the UI. Use AzureRM for standard resources and the versioned SQL API through AzAPI for useFreeLimit=true and exhaustion AutoPause; do not override the offer's 60-minute pause or 32 GB size. SQL may use another policy-allowed region if the free offer is unavailable. Use two contained users restricted to their own databases. Container Apps stay at min 0/max 1 and use public HTTPS, service-side CORS and configured peer URLs; GHCR images are public and tagged by the tested SHA with provenance disabled as directed by the guide.
Alternatives considered: Shared IE resource groups/service-principal secrets and Static Web Apps conflict with the updated guide. VMs, App Service, dedicated profiles and a paid registry violate or add cost to the contract. A separate state Storage account adds an unnecessary resource; a private container in the permitted UI account keeps state separate from public $web. Source-controlled state or plaintext CI artifacts expose secrets. Paid SQL overflow is rejected: exhausting the free allocation pauses the database instead. Hardcoded regions are rejected because student policies differ. Portal changes after setup would drift from the reproducible configuration.
Consequences: Costs are metered rather than guaranteed to be literally zero: Storage uses stored bytes and requests, Log Analytics uses ingestion/retention, Consumption uses active resources, and SQL consumes the student free allowance until it pauses. Containers scale to zero, but SQL waits 60 idle minutes before pause. Initial and resumed requests may receive 503 while startup migrations and bounded ODBC retries finish. Startup probes allow five minutes; CD health checks must allow several minutes and verify both healthy own databases and the tested version. Database-scoped migration locks already guard overlapping startup even with single-replica settings. Initial setup runs the course placeholder until SQL users exist, then the pipeline replaces it with the real images. No repeated drop/recreate/reset is permitted. At 100x traffic, identity validation on each protected Groups request, frequent chat polling, short-lived DB connections and the global Groups write lock become bottlenecks. Beyond the assignment's quota, reassess polling/backoff and caching, finer-grained transaction locks, connection reuse and a separately approved higher replica/database budget; do not simply increase limits here. November 20 evidence update: student eligibility, scoped OIDC, Germany West Central provisioning, actual free SQL settings and exact-version database health were verified by real CD; 22 seeded category IDs/names survived redeployment. Full pause/resume behavior, actual cost review and the later populated-table migration evidence remain open. See CLAUDE_HANDOFF.md and AZURE_DEPLOYMENT.md for the verified run links and limits.

Date: 2026-11-20
Status: Decided; same-SHA Azure deployment verified 2026-11-20
Context: Each domain needs independent tests, coverage, contract checks and image builds, and every main deployment must correspond to the exact tested source. CI must never touch Azure SQL. The updated guide uses GitHub OIDC and Storage static hosting, and initial identity/database setup has different permissions from ordinary app releases.
Decision: Make ci.yml reusable through workflow_call. Feature pushes/PRs run it directly; main's deploy workflow calls it once and requires success before publishing either full-SHA image. CI retains monolith regressions, split-import checks, per-service lint/OpenAPI/migration drift/70% coverage, actual local SQL Server Compose/image checks, two-process HTTP integration, real-browser workflows and mocked infrastructure/deployment guards. Pin infrastructure tooling and provider checksums. Production is serialized without cancelling in-flight applies. No DB/identity credentials enter CI. The documented initial setup generates passwords directly into GitHub secrets, never files, and creates scoped identity/trust/read access. A first deployment uses course placeholders while contained users are created; its temporary runner-IP firewall rule is removed even on failure. Subsequent deployments preserve databases, users and migration history. Until an actual student subscription is enabled and setup succeeds, main can publish tested images but must explicitly report Azure deployment pending, never count that as successful CD.
Alternatives considered: Separate unlinked CI/CD workflow runs can deploy the wrong SHA or trigger twice. Always deploying latest breaks traceability. Running tests on Azure SQL consumes credit and couples CI to live data. Browser-only stubs cannot demonstrate a real server-side seam. Replacing every test with Compose slows feedback unnecessarily; keep fast tests plus the real SQL/container gate. Giving the runtime identity subscription-wide rights or putting credentials in variables/artifacts is unnecessary. Automatic database replacement on a failed plan risks data loss and is rejected. Manual portal fixes after setup cause configuration drift.
Consequences: Local/unit tests prove domain rules and guards; actual Compose checks SQL compatibility and database isolation; browser checks prove the core UI-to-Groups-to-Discovery flow. Request metadata logs and health provide narrow operational signals without bodies/credentials. Deliberate gaps are real Azure eligibility/region/RBAC/image visibility, provider/CDN availability, live cold-start behavior, image-upload/moderation/collection UI parity, and before/after Azure migration evidence; mocked tests do not close these gaps. November 20 evidence update: the owner supplied the actual system.schema.json; it is committed unchanged with system.yaml, and tools/check_system.py is a passing CI gate. Main CD run 44745670962 succeeded at 181474919a9451414fd6a6087e6d681c8a737c0a. Azure browser checks covered Discovery, distinct configured API addresses and exact-version own-DB health; authenticated production flows, partial failure, default-map layout and the later preserving migration are separate open items in CLAUDE_HANDOFF.md. Preserve genuine failed/fixed runs and real successful main CD evidence; do not manufacture failures. Failed deployment leaves owned data intact, requires diagnosing logs and a forward fix, and does not create an extra commit merely to record the failure.

## [10]. Defer user-uploaded images (posters, profile pictures, group photos)
Date: 2026-11-23
Status: Decided; revisit when the trigger below is met
Context: In Assignment 1 organizers could upload an event poster, and people could add profile and group photos; the monolith stored them under a local media folder. In Assignment 2 the services run as Azure Container Apps that scale to zero with at most one replica, and a container's local filesystem is discarded when it restarts or scales to zero. Keeping uploads would need storage that outlives the container, an upload path from the browser that does not run through the API's request timeout, and a rule for who may delete or replace a file. Only the Discovery and Groups APIs and a static UI exist, so no component currently owns uploaded files.
Decision: Do not build image upload in this assignment. Events and artists use the bundled poster and photo files that ship with the static UI (`ui/assets`, referenced by `demo_poster` and `photo` paths), and the upload and crop screens are left unconverted from Assignment 1. The services keep their existing image-validation helper (`config/images.py`) and the `MEDIA_ROOT` setting, but nothing in the deployed UI or the OpenAPI documents offers a way to upload a file (the only image endpoints are downloads of already-stored files), so no data is written to the container's local disk that would silently disappear. Remaining pages must show the bundled artwork, never a broken image link.
Alternatives considered: Write uploads to the container's local disk: rejected because files vanish on every restart or scale-to-zero, which would look like random data loss. Store uploads in the existing Storage account's public `$web` container: rejected because it mixes user content with the released UI files, lets a UI deployment overwrite or delete uploads, and gives no ownership or deletion control. Store images as binary columns in the SQL databases: rejected because it grows the free SQL allowance (32 GB, shared with all rows), slows backups and makes the paused database wake for every image request. Add a separate private Blob container with short-lived upload links issued by the owning service: this is the right design, but it adds a Storage role assignment, link-signing code, size and type limits enforced at the storage edge, orphan cleanup and a CORS policy for the browser, all for a feature the assignment does not require and that cannot be verified here without a real user flow.
Consequences: Event creation keeps working with a bundled poster only, profile and group photos stay blank, and the A1 upload and crop screens are not available in the deployed app; this is a visible reduction in feature parity and is stated in the report. Nothing about the data model blocks the feature later: poster and photo columns already hold only a path string. It becomes worth building when real organizers need their own posters (more than a handful of events whose artwork cannot be a bundled file) and the budget allows a private Blob container; the first version should use per-service private containers with upload links that expire in minutes, a size and content-type check on the service, and a cleanup job for files that were never attached to a record. Until then, a deliberate gap in ADR 9's test list: there is no automated test of media persistence because there is no media feature to test.
